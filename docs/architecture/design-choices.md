# Architecture design choices and trade-offs

This document explains **why the implemented Image-to-LEGO system uses its current stack**, the alternatives considered and the costs of each choice. It complements the [architecture overview](README.md) and the individual [architecture decision records (ADRs)](../decisions/). Implementation, migrations and current Terraform take precedence over earlier planning drafts when their assumptions differ.

## Key decisions

| Decision | Why this fits the project | Trade-off / boundary | Implementation evidence |
| --- | --- | --- | --- |
| **Supabase-hosted PostgreSQL instead of NoSQL** | Projects, jobs, runs, artifacts and publication intents need foreign-key relationships, transactional state changes, unique idempotency keys, indexed lookups and row-level authorization. | SQL migrations, connection and role management add complexity. The database architecture supports indexing and operational scaling, but high-load query performance is **not independently benchmarked**. | [Migrations](../../supabase/migrations/), [ADR-001](../decisions/ADR-001-postgresql-supabase.md) |
| **Supabase Auth + FastAPI-verified JWT + PostgreSQL RLS** | Managed login reduces authentication work; the API validates tokens and enforces project ownership, with RLS as a database-side boundary rather than trusting a browser-supplied owner ID. | JWKS verification, separate database roles and transaction-local ownership context require precise configuration; the browser does not access application tables directly. | [Auth verifier](../../backend/app/core/auth.py), [migrations](../../supabase/migrations/) |
| **Private Azure Blob Storage with scoped SAS, rather than Supabase Storage or database BLOBs** | Images, GLBs and LEGO JSON remain out of PostgreSQL. Direct browser upload/download avoids routing large files through the API, while short-lived object-scoped SAS limits access. | CORS, managed identities and SAS lifetimes need care; PostgreSQL deletion cannot atomically remove Azure files, so orphan cleanup is separate. **Supabase Storage is not used.** | [Blob adapter](../../backend/app/providers/blob_storage.py), [Blob sweep](../../backend/app/workers/blob_sweep.py), [ADR-005](../decisions/ADR-005-azure-blob-storage.md) |
| **Python 3.12 + FastAPI + modular monolith, rather than Node.js/Go or many microservices** | The API shares validated settings and domain code with Python's `trimesh`/OR-Tools conversion engine; Pydantic/OpenAPI and route→service→repository/provider boundaries keep contracts explicit. | Python's CPU and memory costs make synchronous mesh work unsuitable for HTTP workers. The codebase shares a release cadence; generation and conversion run in separate worker processes. | [Backend dependencies](../../backend/pyproject.toml), [API](../../backend/app/api/), [ADR-002](../decisions/ADR-002-python-fastapi.md), [ADR-006](../decisions/ADR-006-modular-monolith.md) |
| **Versioned REST jobs + browser polling, rather than gRPC or WebSockets** | `POST` initiates asynchronous reconstruction/conversion, and `GET` checks a persisted job state; conventional JSON/HTTP contracts work naturally in the browser and are easy to test. TanStack Query manages repeated requests and cached server state. | Polling produces extra reads and a short status-update delay. No realtime push or gRPC performance advantage has been demonstrated for this workflow. | [API routes](../../backend/app/api/), [frontend source](../../frontend/src/), [ADR-003](../decisions/ADR-003-rest-api.md) |
| **React + TypeScript + Vite + TanStack Query, rather than a server-rendered framework** | The product is primarily an authenticated interactive workspace, not an SEO-driven public site. Typed UI models and server-state caching suit project, artifact and job workflows. | The SPA gives up SSR/SEO benefits and depends on client-side JavaScript; TanStack Query adds a library and cache-invalidation discipline. The actual frontend uses **npm**, not pnpm. | [Frontend package](../../frontend/package.json), [frontend source](../../frontend/src/) |
| **Three.js + React Three Fiber for inspection** | React-integrated WebGL viewers let users inspect reconstructed GLBs and discrete LEGO placements within the same project workflow. | Browser GPU, memory and model size affect responsiveness; visual inspection alone does not establish mechanical buildability. | [Frontend components](../../frontend/src/components/) |
| **Transactional outbox + Azure Service Bus + fenced worker attempts, rather than inline processing or direct queue sends** | A job, its parameters and publication intent are committed together; queues isolate slow paid generation and CPU conversion from request latency. Leases, idempotency and fencing address duplicate deliveries and stale workers. | At-least-once delivery is **not** distributed exactly-once execution. A send with uncertain outcome may require manual reconciliation, while an ambiguous fal.ai submission must not be automatically repeated. | [Outbox](../../backend/app/outbox/), [workers](../../backend/app/workers/), [migrations](../../supabase/migrations/), [ADR-008](../decisions/ADR-008-durable-worker-release-coordination.md) |
| **Separate ACI generation/conversion workers, not an autoscaling worker pool** | Long-running provider calls and CPU-intensive conversion do not consume API request capacity, and the two task types can be operated independently. | Current ACI groups use `restart_policy = "Never"` and a controlled lifecycle; **queue-depth autoscaling and measured heavy-load throughput are not implemented claims**. | [Compute Terraform](../../infra/terraform/application-compute/README.md), [workers](../../backend/app/workers/) |
| **Azure Container Apps frontend + Linux App Service API, rather than the original Static Web Apps / all-Container-Apps proposal** | The actual development topology uses an Nginx-hosted frontend Container App with an `/api/` reverse proxy, a separate FastAPI App Service, private ACI workers, ACR, Key Vault and Log Analytics. It suits the deployed subscription/resources without running VMs or Kubernetes. | More Azure products and configuration boundaries create operational overhead; the B1 API plan and existing ACI groups are **not evidence of horizontal scaling under heavy load**. Earlier ADRs are historical where they describe different target hosting. | [Compute Terraform](../../infra/terraform/application-compute/README.md), [lifecycle runbook](../deployment/azure-terraform-lifecycle.md), [ADR-007](../decisions/ADR-007-container-apps-frontend-hosting.md) |
| **Managed identities + Key Vault + ACR + split Terraform state and gated CI/CD** | Distinct identities limit Azure permissions; Key Vault keeps privileged secrets out of images; shared durable infrastructure is isolated from replaceable compute, and CI checks code/build/infra changes. | Identity/RBAC and deployment gates need careful operations. GitHub Actions definitions do **not** prove that fully automatic production deployment or release mutation is active. | [Shared Terraform](../../infra/terraform/shared/README.md), [CI](../../.github/workflows/ci.yml), [release guide](../deployment/github-actions-azure-cicd.md), [ADR-009](../decisions/ADR-009-fenced-release-controller.md) |
| **Deterministic, catalogue-constrained LEGO conversion instead of naive voxel cubes** | The conversion stage maps reconstructed geometry onto stud/plate dimensions, legal part/colour combinations and bounded fitting, with versioned silhouette and limited mechanical diagnostics. Application routing supports V3–V7; the UI exposes V4/V6 and experimental V7. | Finer detail is computationally costly, source meshes may be imperfect, and not every catalogue part is eligible for production fitting. Connectivity and insertion checks are **not** proof of a physically stable or hand-assemblable model. Later M-series research remains offline unless explicitly integrated. | [Converter](../../backend/app/conversion/core.py), [catalogue](../../lego_catalogue/README.md), [experiments](../testing/) |
| **Layered, largely offline automated testing instead of relying only on paid cloud end-to-end tests** | Python Pytest/Ruff/Mypy, frontend Vitest/ESLint/type checking, deterministic synthetic meshes, fakes and isolated PostgreSQL checks make regressions repeatable without calling fal.ai or mutating real Azure resources on ordinary test runs. | Mocks cannot prove external provider uptime; a committed workflow is not a substitute for measured coverage or sustained production load tests. Use controlled live smoke tests only when intentionally authorized. | [Backend tests](../../backend/tests/), [CI](../../.github/workflows/ci.yml), [testing guide](../testing/README.md) |

## Scalability and evaluation: what is and is not established

The relational schema and indexes, stateless API patterns, direct Blob transfer, persistent queues and separate workers are **scalability-oriented design choices**. They reduce contention and support controlled growth, but the current development footprint does **not** demonstrate automatic queue-based worker scaling, load-balanced API replicas, or consistently low latency under heavy load. Such claims require recorded concurrency, dataset/workload, throughput, p50/p95 latency, failure rates and Azure cost measurements—not diagrams alone. Refer to the [root README's success criteria](../../README.md#engineering-success-measures-and-boundaries) and [release controls](../deployment/github-actions-azure-cicd.md).
